## 1. 実現したい仕様（運営者の要望）

### 機能1: 空き枠カード全体をタップ可能にする
「自分で選んだ場所でプランを作る」の空き枠（例:「午前 おでまるが提案します」）について、
右側の「＋追加」ボタンだけでなく **カード全体をタップ**しても施設選択画面が開くようにする。
どの枠を押したかを保持し、選んだ施設をその枠へ入れる。

### 機能2: 登録済み施設の名前検索
施設選択マップ（map.html）の上部に検索窓を設置する。
- 既存の選択対象施設を **名前の部分一致**で検索
- 候補をタップすると該当地点へ地図を移動
- 施設詳細（シート）または該当ピンを表示
- そこから対象枠へ追加

### 機能3: 未登録場所の一時追加
検索結果にない場合「見つからない場所を追加」を表示する。入力項目:
- 場所の名前
- 住所 または 地図上の位置
- **滞在時間**

追加した場所は**公開施設データには登録せず**、そのユーザーの現在のプラン内だけで使う。
用途: 祖父母宅・友人宅・習い事・未掲載施設を、既存施設と組み合わせる。

## 5. 実装上の注意点（ここが本文書の核心）

### 5-1. 内側ボタンとのイベント衝突（機能1）
空き枠カードの div の中に既に **「🍱お弁当」(cpBento)・「＋追加」(cpOpenAdd)・「✕」(cpRemoveRow)** のボタンがある。
行 div に `onclick` を付けると内側ボタンのクリックも拾ってしまう。

**対策（どちらか）**
- 内側の各ボタンに `event.stopPropagation()` を追加する
- カード側の onclick 冒頭で `if (event.target.closest('button')) return;` でガードする

**さらに安全策**: 埋まっている枠の行には ↑↓✕ があるので、**空き枠の行だけ**にハンドラを付ける。

### 5-2. 検索時にチェーン店・児童館のフィルタを自動ONにする必要性（機能2）
map.html はフィルタ `matches(s)` に合致しないマーカーを `apply()` で**地図から remove している**。
チェーン店・児童館は既定で非表示のことがある。
→ **検索でヒットさせても地図にピンが無い**状態になる。

**対策**: 検索結果を選んだとき、
- 該当スポットが現在のフィルタで非表示なら、該当フィルタ（チェーン/児童館など）を**自動でONにして `apply()` を再実行**する
- または該当マーカーだけ `markers[i].addTo(map)` で個別に出す

**これが機能2で唯一の落とし穴。** 忘れると「検索でヒットするのに地図に出ない」バグになる。

### 5-3. 滞在時間フィールド `__stay`（機能3）
既存に滞在時間のフィールドは**無い**。`stayMinutes(s)`（497）が種別から自動算出し、
`customGenerate5()`（2788）は mStay=60/90 で固定、午後は逆算している。

**対策**: カスタム地点に `__stay: <分>` を持たせ、
- `stayMinutes(s)` の冒頭で `if (s.__stay) return s.__stay;`
- `customGenerate5()` の滞在決定箇所でも `__stay` を優先
の**2箇所**を改修する。保存は `cpSaveSlots()`（2337）と `cpResolveItem()`（2331）に1フィールド足すだけ。
UIは滞在時間セレクト（30/60/90/120分）を想定。

### 5-4. 座標なし地点による NaN 伝播 — **最も危険**
`legMinutes()`（414）/`driveMinutesFrom()`（406）/`haversineKm()`（371）/`cpPrevSpot()`（2448）は
いずれも `latitude`/`longitude` が数値であることを前提にしている。

**緯度経度なしのカスタム地点を1件でも許すと、NaN がタイムラインの全行（移動時間・到着時刻・帰宅時刻・運転合計）に伝播する。**

**対策**: 住所解決（国土地理院API）または地図タップ座標を**必須**にし、
座標が取れなければ登録させない。現行の `cpAddPlace()` は住所必須なのでこの点は既に担保されている。
地図タップを追加する場合も同様に座標必須を維持すること。

### 5-5. 共有URLでカスタム地点が消える
`buildShareUrl()`（2129）は **スポット名のみ**をクエリ化し、
`restoreFromShare()`（2199）は `SPOTS.find(name)` で公開データから解決する。
→ **カスタム地点は共有URLで無言で欠落する。**

**対策（段階的）**
- 最小対応: 共有時に temp 地点が含まれていたら「入力した場所は共有できません」と注記を出す
- 将来対応: 共有URLに temp 地点の name/lat/lng を含める（URL長とプライバシーに注意。祖父母宅の座標がURLに乗る点は要検討）

**再編集（`editCustom()` 2783 → localStorage経由）は temp も保持されるので問題なし。**

### 5-6. map.html と plan.html で飲食判定が別実装
- map: `isLunchableSpot(s)`（479）
- plan: `isLunchable(s)`（2267）＋ `cpIsFoodSpot()`（2275）

**同じロジックが2箇所に重複している。片方だけ直す事故が起きやすい。**
飲食まわりを触るときは必ず両方を確認すること。
なおカスタム地点は `play_types:['indoor']` なので、昼枠には `__temp` 例外（`cpIsFoodSpot`）でのみ入る。
**map側の slotpick は `__temp` を知らないため、昼枠へのカスタム地点投入は plan 側限定。**

### 5-7. 枠数・上限まわり
- `makeCustomPlanFromSel()`（map.html:527）の shape 算出は**2026-08-16に修正済み**
  （飲食なしは `shape = Math.min(5, Math.max(3, total+1))`、飲食ありは従来どおり）
- 「5件まで」「飲食なしは4件まで」の上限チェックは `toggleSel()`（482）内にあり、
  **slotpick モードは早期 return するためこの制限を通らない**
  → 検索窓を「slotpick用」と「通常の複数選択用」の両方で使うなら、通常モードでは必ず `toggleSel()` を経由させること
- 枠は**最大5**。検索経由の追加も上限チェックを通す

### 5-8. 営業時間まわり（影響は小さい）
`closingInfo()`/`isClosedOn()`/`parseBusinessHours()`/`isUnverifiedHours()` は
`business_hours=null` で安全側に落ちる。
カスタム地点は `cpSuggest()` の候補生成に元々入らないため影響なし。
※ 2026-08-16 に `ALLOW_UNVERIFIED_HOURS=true`（営業時間未確認スポットの全開放）を入れている。
　カスタム地点は営業時間なしなので「🕐 営業時間は要確認」の表示対象になる可能性がある。表示可否を確認すること。

## 6. カスタム地点の最小データ構造

既存の雛形 `tempSpot(name,lat,lng,addr)`（plan.html:2285）:
```js
{ name, latitude, longitude, city: addr, play_types: ['indoor'], is_free: true, __temp: true }
```

**必須（無いと落ちる）**
| フィールド | 理由 |
|---|---|
| `name` | 表示・重複判定・共有・`cpMissingSelected` の名前一致 |
| `latitude` / `longitude` | 移動時間計算。**null だと NaN 伝播（5-4参照）** |
| `play_types`（配列） | `includes` を無防備に呼ぶ箇所が多数あるため、空配列でも必ず配列で持つ |
| `__temp: true` | 昼枠許可（`cpIsFoodSpot`）とUI表記 |

**入れると安定（任意）**
| フィールド | 理由 |
|---|---|
| `city` | 表示 |
| `is_free: true` | `parsePrice` → 予算警告の回避 |
| `business_hours: null` / `closed_days: null` | パーサーは null 安全 |
| `is_chain: false` / `is_jidokan: false` | 各種フィルタの明示 |
| **`__stay: <分>`** | **今回追加する滞在時間（5-3参照）** |

### 12-1. 赤枠タップの遷移先 — `cpOpenAdd` か `cpGotoMap` か

**運営者の当初の希望は「赤枠を押したら“検索窓付きマップ”を直接開く」。**
本文書 7章の段階1で `cpOpenAdd(i2)`（＝候補パネルを開く）と書いたが、**それは本命ではない。**
本命は **`cpGotoMap(i2)`**（＝`map.html?slotpick=<枠>` へ遷移）である。

決めるべきは次のどちらか:

| 案 | 赤枠カード全体 | 右の「＋追加」 | 評価 |
|---|---|---|---|
| **A（運営者の推し）** | 検索窓付きマップ（`cpGotoMap`） | **同じく**検索窓付きマップ（`cpGotoMap`） | **両方をマップへ統一。** 挙動が1つで迷いがない。既存の候補パネル（`cpSuggest`）は使わなくなる |
| B | 検索窓付きマップ（`cpGotoMap`） | 従来どおり候補パネル（`cpOpenAdd`） | 2つの入口が別動作。近場のおすすめをすぐ見たい人には候補パネルが速いが、UIの説明が要る |

**運営者の意向は A（両方とも検索付きマップへ統一）。**
A を採る場合の影響:
- `cpOpenAdd()` / `cpSuggest()` は**呼ばれなくなる**（コードは残すが導線から外れる）。削除はしないこと（将来戻す可能性・他からの参照確認が必要）
- 「近くのおすすめを出す」機能が導線上から消えるため、**マップ側の初期表示で近場が見えるか**を確認する（`cpGotoMap` は出発地中心で開くか？ 開かないなら `?lat=&lng=` 等で中心を渡す検討）
- **機能2（名前検索）が先に入っていないと、マップに飛ばす価値が下がる。** A を採るなら段階3（名前検索）を段階1とセットで出すか、少なくとも近接して出すのが望ましい
  → **順序の再検討が必要**（本文書7章の「1→2→3」は B 前提。A なら「1と3をセット」または「3→1」が合理的）

**未決のまま実装しないこと。**

### 12-2. 「見つからない場所を追加」を押したあとの遷移

検索窓は **map.html**、既存の住所追加 `cpAddPlace()` は **plan.html** にある。
検索0件のとき「見つからない場所を追加 ＋」を押した後の動きが未確定。

| 案 | 内容 | 評価 |
|---|---|---|
| **A（推奨）** | **slotpick を保持したまま plan.html へ戻り、対象枠の既存追加フォーム（`cpAddPlace` 周り）を開く** | **重複実装を避けられる。** 住所解決・座標必須・`__stay`・保存形式がすべて既存のまま使える。安全 |
| B | map.html 内に新しい入力UI（名前・住所/地図タップ・滞在時間）を作る | 画面遷移がなく滑らかで、**地図タップで座標を取る**なら自然。ただし入力UI・住所解決・保存処理が plan 側と二重実装になり、5-6 と同じ「片方だけ直す事故」を生む |

**推奨は A。** 実装イメージ:
```
map.html 検索0件 → 「見つからない場所を追加 ＋」
  → ./plan.html?custom=1&addplace=<枠番号>  等で戻す

  その枠の住所追加フォームを自動で開く（cpSetTarget → cpAddPlace のUIを展開）
```
必要な差分は plan.html 側の**起動時パラメータ処理 5〜10行**程度。

※ 将来 B（地図タップで座標指定）をやりたくなった場合は、**入力UIは plan 側に一本化したまま、
map.html は「タップした座標を返すだけ」**にすると二重実装を避けられる
（例: `plan.html?custom=1&addplace=<枠>&lat=&lng=` で座標だけ持ち帰る）。

## 13. 12章を踏まえた実装順序（改訂案）

12-1 で **A（両方マップへ統一）** を選ぶ場合、7章の順序は次のように読み替えること:

| 順 | 内容 | 対象 | 規模 |
|---|---|---|---|
| 1 | **名前検索**（map.html） | map.html | 60〜90行 |
| 2 | **赤枠カード全体タップ → `cpGotoMap(i2)`**／「＋追加」も `cpGotoMap` へ統一 | plan.html | 5〜10行 |
| 3 | **「見つからない場所を追加」→ plan.html へ戻して住所追加フォームを開く**（12-2案A） | map.html + plan.html | 15〜25行 |
| 4 | **未登録場所の滞在時間 `__stay`** | plan.html | 30〜40行 |
| 5 | **共有URL対応**（注記 or temp埋め込み） | plan.html | 5〜30行 |

理由: A では赤枠タップの遷移先がマップなので、**マップに検索窓が無い状態で先に導線だけ変えると体験が悪化する**。
検索窓を先に入れてから導線を切り替えるのが安全。

12-1 で **B** を選ぶ場合は、7章の順序（空き枠タップ → 未登録場所 → 名前検索 → 共有対応）のままでよい。
